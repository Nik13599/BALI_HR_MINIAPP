# BALI — обязательная Telegram-авторизация в релизной версии

## Статус документа

Этот документ фиксирует обязательное различие между текущей браузерной демо-версией и будущей релизной версией BALI.

При проектировании серверной архитектуры, API, базы данных, прав доступа и клановых чатов необходимо руководствоваться этим разделением.

---

# 1. Демо-версия

Текущая демо-версия может запускаться в обычном браузере без обязательной привязки к Telegram.

Это допускается исключительно для:

- демонстрации интерфейса;
- проверки пользовательских сценариев;
- тестирования дизайна;
- презентации партнёрам;
- локальной разработки;
- проверки отдельных функций без Telegram-контейнера.

Демо-режим не считается релизной системой идентификации пользователя.

Данные, роли, права и действия, созданные внутри автономной браузерной демо-версии, не должны автоматически считаться подтверждёнными релизными данными.

---

# 2. Релизная версия

После выхода приложения в релиз вход в пользовательскую часть BALI разрешён только через Telegram Mini App.

Пользователь без подтверждённой Telegram-сессии не может:

- открыть пользовательское приложение;
- получить профиль BALI;
- просматривать BALI People;
- вступать в кланы;
- открывать клановые чаты;
- читать или отправлять сообщения;
- голосовать в опросах;
- открывать внутренние прикреплённые мероприятия;
- отправлять подарки;
- приглашать пользователей;
- получать пользовательские данные через API;
- выполнять любые действия от имени пользователя.

Обычная регистрация по логину и паролю, телефону, электронной почте или через браузерную форму для пользовательской части не предусматривается.

---

# 3. Telegram как обязательный источник идентификации

В релизной версии основной идентичностью пользователя является подтверждённый Telegram-пользователь.

Для каждого аккаунта BALI необходимо хранить связь как минимум между:

- внутренним ID пользователя BALI;
- Telegram user ID;
- датой первого подтверждённого входа;
- датой последнего подтверждённого входа;
- статусом аккаунта;
- служебными признаками блокировки или ограничения.

Telegram username, имя, фамилия и фотография могут изменяться и не должны использоваться как единственный постоянный идентификатор.

---

# 4. Проверка входа на сервере

Факт открытия Mini App в Telegram сам по себе не должен считаться достаточным подтверждением личности только на стороне интерфейса.

Релизный сервер обязан проверять данные авторизации Telegram до создания пользовательской сессии.

После успешной проверки сервер создаёт собственную ограниченную сессию BALI, связанную с конкретным Telegram user ID и внутренним ID пользователя.

Клиент не должен иметь возможности самостоятельно передать произвольный Telegram user ID и получить доступ к чужому аккаунту.

Все защищённые API должны определять пользователя из проверенной серверной сессии, а не из ID, переданного клиентом в теле запроса.

---

# 5. Связь с правами кланового чата

Telegram-авторизация подтверждает личность пользователя, но не предоставляет ему права внутри клана автоматически.

После подтверждения Telegram-сессии сервер отдельно проверяет:

1. существует ли активный аккаунт BALI;
2. не заблокирован ли пользователь;
3. является ли пользователь действующим участником конкретного клана;
4. какую роль он имеет в этом клане;
5. какие отдельные разрешения выданы ему администратором;
6. не ограничен ли он во временном порядке;
7. разрешена ли запрошенная операция.

Таким образом, доступ к чату требует одновременно:

- подтверждённой Telegram-сессии;
- активного аккаунта BALI;
- действующего членства в нужном клане;
- соответствующего серверного разрешения на конкретную операцию.

---

# 6. Административная часть

Обязательный вход через Telegram относится к пользовательскому Mini App.

Административная часть BALI остаётся отдельным веб-приложением.

Для неё должна использоваться самостоятельная защищённая административная авторизация с отдельными ролями и журналом действий.

Открытие административной панели не должно быть доступно обычному Telegram-пользователю только на основании входа в Mini App.

Пользовательская Telegram-сессия и административная веб-сессия являются разными контурами доступа.

---

# 7. Разделение режимов окружения

Система должна явно различать окружения:

- `demo` — автономная браузерная демонстрация;
- `development` — разработка;
- `staging` — предрелизная проверка;
- `production` — релизная версия.

В `production` запрещено включать обход Telegram-авторизации через:

- демо-пользователя;
- подстановку ID в URL;
- выбор аккаунта из списка;
- сохранённые локальные данные браузера;
- скрытую кнопку разработчика;
- query-параметр;
- клиентский флаг;
- прямой вызов API без проверенной серверной сессии.

Демо-механики не должны попадать в production-сборку либо должны быть полностью отключены серверной конфигурацией.

---

# 8. Требования к данным демо-версии

Демо-версия может использовать тестовые профили, локальное состояние и имитацию действий.

При этом необходимо визуально и технически обозначить, что это демонстрационные данные.

Рекомендуется:

- использовать отдельную демо-базу или локальные данные;
- не смешивать демо-пользователей с production-пользователями;
- не переносить демо-роли и начисления в production;
- не считать демо-посещения подтверждёнными;
- не считать демо-голоса официальными;
- не использовать демо-сообщения как историю реального клана.

---

# 9. Поведение при открытии релизной версии вне Telegram

Если пользователь открывает релизный адрес Mini App в обычном браузере, система не должна показывать рабочую пользовательскую сессию.

Допустимый экран:

- логотип BALI;
- сообщение «Откройте приложение через Telegram»;
- кнопка перехода в официального Telegram-бота или Mini App;
- краткое объяснение, что вход доступен только через Telegram.

Нельзя предоставлять гостевой доступ к BALI People, профилям, кланам, чатам или API.

---

# 10. Критерии готовности

Функционал авторизации считается готовым, если:

1. Демо-версия продолжает открываться в обычном браузере для презентации и тестирования.
2. Демо-режим явно отделён от production.
3. Релизная пользовательская версия открывает рабочую сессию только после подтверждённого входа через Telegram Mini App.
4. Открытие production-адреса в обычном браузере не даёт доступ к пользовательским данным.
5. Клиент не может подменить Telegram user ID и открыть чужой профиль.
6. Все защищённые API используют пользователя из проверенной серверной сессии.
7. Доступ к клановому чату дополнительно проверяет активное членство в клане.
8. Права главного, участника и делегированные права проверяются отдельно от факта Telegram-входа.
9. После выхода или исключения из клана доступ к его чату закрывается сервером.
10. Заблокированный пользователь не получает рабочую сессию либо получает строго ограниченный режим по решению администратора.
11. Демо-данные не смешиваются с production-данными.
12. Административная веб-панель использует отдельную систему авторизации.
13. В production отсутствует клиентский или URL-обход Telegram-входа.
14. Все неуспешные попытки доступа к защищённым API возвращают отказ без раскрытия данных.
15. Критические события входа, блокировки и административного доступа записываются в служебный журнал.

---

# 11. Итоговая обязательная схема

## Текущая демо-версия

Обычный браузер → демо-режим → тестовые или локальные данные → функции для демонстрации.

## Релизная пользовательская версия

Telegram Mini App → серверная проверка Telegram-авторизации → серверная сессия BALI → проверка аккаунта → проверка членства и прав → доступ к разрешённой функции.

## Административная версия

Веб-админка → отдельная административная авторизация → проверка роли администратора → доступ к служебным функциям.

Главное правило: **без подтверждённого Telegram-пользователя вход в релизную пользовательскую часть BALI невозможен**.
